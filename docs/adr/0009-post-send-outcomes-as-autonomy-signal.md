# 0009 — Post-send outcomes as an autonomy signal

## Context

Every signal in the pre-send system is a *prediction*. Judges score the campaign, the
controller decides, it ships — and nothing ever checks whether the prediction was
right. That is a real hole, because judges share the blind spots of the thing they
judge: if the `brand_voice` judge has a systematic weakness, the agent sails through
the gate and into the inbox. It also leaves the hardest question about the framework
unanswered — *how do you know your evals are any good?* Without real outcomes, the
only answer is "I calibrated them against my own labels."

## Decision

Close the loop with a post-send deliverability signal.

* An **outcome simulator** (`outcomes/simulator.py`) produces deliverability metrics
  for each sent campaign, deterministic per `(seed, run_id, scenario)`. Outcomes
  correlate with pre-send quality but imperfectly: the Gaussian noise is wide enough
  that a well-scored campaign occasionally breaches anyway. A tautological simulator
  (good scores ⇒ good outcomes) would make the loop decorative, so a test asserts
  that some well-scored campaigns breach. Scenarios: `nominal`, `judge_blindspot`,
  `degrading`.
* A **breach is handled exactly like a critical eval failure** — the *same* path, not
  a parallel one: demote to Tier 0, downgrade in-flight campaigns of that type to
  review, open probation, and require the golden-subset challenge to earn the tier
  back. A clean outcome confirms the run (which already counted in the Wilson window
  at send time).
* The ledger gains a third entry kind, **`outcome`**, linked to the originating run
  and carrying the metrics and the decision. Tier state stays a pure fold of
  transitions — an outcome entry records a fact and never itself mutates state; any
  demotion it triggers is its own transition — so replay including post-send events
  reconstructs the same state (P4).
* A run that **passed every eval but breached** is classified
  `eval_passed_outcome_failed` — a confirmed case where the judges were wrong — and
  auto-flagged into `evals/candidates/` with its scores, content, and outcomes for
  human triage into the golden set.

## Alternatives considered

**Leave outcomes out and trust calibration.** Cohen's κ says judges agree with a
human on labelled cases; it says nothing about what fraction of genuinely harmful
campaigns they catch in production (recall). Only real outcomes reveal the misses.
See [docs/economics.md](../economics.md) for why recall, not the Wilson pass rate, is
the economically relevant metric.

**A parallel demotion path for deliverability.** Rejected: a second path is a second
thing to get wrong. Reusing the critical-failure path means demotion, probation, and
the in-flight downgrade behave identically however the failure was discovered.

## Consequences

The loop improves the *evaluator*, not just the agent: every discovered blind spot
becomes a test case, so the gate that guards promotion sharpens over time. The
console gains a **Run Simulation** control and an **Outcomes** view (predicted quality
vs actual deliverability, a breach timeline, and a "judge blind spots found" count),
which is also the strongest 90-second moment in a demo — a campaign clears every gate,
the world disagrees, the tier drops automatically, and the disagreement becomes the
next agent's test. The simulator is deterministic so all of this is reproducible; the
candidate flags are gitignored because they are regenerated by the loop.
